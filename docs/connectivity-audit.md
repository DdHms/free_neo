# Connectivity research

Research snapshot: 2026-11-10. These are upstream claims, not verification on this drone.

- [DJI SDK compatibility](https://support.dji.com/help/content?customId=01700000763&documentType=&lang=en&paperDocType=ARTICLE&re=US&spaceId=17): Neo 2 is listed without Mobile SDK support.
- [dji-neo2-lan-client](https://github.com/smichea/dji-neo2-lan-client): MIT; experimental Python/Linux Neo 2 BLE setup, Wi-Fi transport, video, telemetry and limited flight trials. Linux BlueZ and NetworkManager dependencies require investigation on macOS. Its authors report incomplete flight control and failsafe validation. Pin a revision and inspect implementation before reuse.
- [neo-control](https://github.com/lslv1243/neo-control): MIT; first-generation Neo iOS client and Python DUML codec. Describes BLE registration, Wi-Fi handoff and UDP transport. Neo 2 compatibility is not established.
- [dji-firmware-tools](https://github.com/o-gs/dji-firmware-tools): GPL-3.0; DJI firmware and packet-analysis tools including DUML utilities. Neo 2 compatibility is not established; account for licensing before incorporating code.

Local scan on this Mac was blocked by macOS Bluetooth authorization, including when using the Python app explicitly. No device handshake, telemetry, takeoff or landing has been verified. Android requires its own Bluetooth/Wi-Fi implementation behind equivalent contracts.

## Hardware observation — 2026-11-11

On the user's Mac, a Neo 2 advertising `FFF0` accepted a BLE connection and, after physical confirmation, the reference client's setup obtained Wi-Fi credentials. The reference was used at commit `a80e3e14b96aaa32b9e625c0229c53c45187f930`, with its Linux-only Bluetooth-address check adapted locally for macOS UUIDs. With Ethernet providing the internet route, the Mac joined the drone over Wi-Fi; the drone's local gateway responded to ICMP. A ten-second reference SWUDP session accepted the transport connection and received protocol bytes, but reported application readiness as false. Flight commands, telemetry validity, and landing behavior remain unverified on this aircraft. No flight commands were sent. Credentials and captures were kept outside the project in a private temporary directory.

A subsequent read-only session with the reference client's Wi-Fi service switch completed negotiation and received video and flight-state telemetry. The aircraft reported not flying and motors off. The reference client's generic `application_ready` field is hard-coded to false, including on successful sessions; it should not be interpreted as an error. Its telemetry and battery snapshots still mark flight readiness false and source/physical validation incomplete. This does not validate takeoff, landing, or failsafes. The project provides `neo2-observe` for a repeatable non-flight session.

The reference flight observer was also attached to a read-only Wi-Fi session with the vertical-trial profile. During the session it reported an available control route, motors off, not flying, and 50% battery; it also reported unavailable position, unconfirmed ground state, and unavailable connection origin. No flight action was sent. The reference flight connection owner relies on Linux NetworkManager, Linux interface binding, and Linux Bluetooth addressing, so it cannot be used unchanged as the macOS flight controller. Independent override and link-loss behavior for this Mac/drone setup remain unverified.

The project now includes a macOS-specific UDP binding helper using the macOS SDK's `IP_BOUND_IF`; a local test bound a socket to the drone's Wi-Fi interface and confirmed the source address belonged to its network without transmitting. This helper is not yet integrated into the reference flight owner. The reference owner's retained BLE lifecycle, exclusive device ownership, independent override, and confirmed landing behavior still need a macOS implementation and validation before a real flight demo can run.

The pinned reference's session module was subsequently adapted locally as `neo2_vision.vendor.macos_session`, with upstream MIT license retained. Its socket uses macOS `IP_BOUND_IF` and verifies the drone subnet before sending. A read-only session using this adapted socket completed the Wi-Fi service switch and received video and telemetry. The upstream flight owner and its Linux-specific network and BLE lifetime management have not yet been adapted; socket success does not verify flight safety or cleanup after an airborne failure.

A preliminary macOS adaptation of the reference flight connection owner now retains BLE, checks the existing Wi-Fi route, binds the UDP session to the selected interface and uses the reference supervisor. A live connection-only trial obtained fresh telemetry and closed with verified cleanup, with zero flight commands sent. This is not yet a flight-ready owner: the reference's independent controller process requires Linux `prlimit`, `pidfd_open`, and Unix `SOCK_SEQPACKET`; this Mac reports the latter socket type unsupported. The process isolation, watchdog, and persistent airborne-incident recovery must be adapted and tested rather than bypassed.

A simulation-only macOS watchdog experiment uses a framed Unix stream socket and a separate process running the reference synthetic supervisor. In an offline test the simulated aircraft took off, a parent heartbeat timeout caused a simulated landing, and the supervisor confirmed synthetic ground state. This does not implement real-flight owner recovery, test host failure, or establish physical aircraft failsafes; it is not a production watchdog.

A macOS peer-credential helper was checked against a local socket pair. The simulation-only watchdog also passed a parent-heartbeat timeout test using framed Unix stream sockets, and the PyCharm watchdog simulation demonstrates synthetic takeoff and landing. The production owner adoption protocol, persistent flight incident storage with macOS BLE identifiers, independent process resource controls and real-aircraft failure behavior remain unfinished.

The macOS recovery work now includes a same-user private Unix-socket rendezvous primitive and a persistent incident store keyed by the full macOS BLE UUID. Offline tests verify that the endpoint cannot replace an existing socket or unrelated file, peer credentials are checked, and a synthetic airborne incident survives an abrupt owner exit and cannot be cleared for a different aircraft. These are building blocks only: the watchdog owner does not yet use this rendezvous, process identity across PID reuse is not established, and no production owner takeover or real flight has been validated.

The macOS incident store now passes an abrupt-owner-exit persistence test. A nonblocking framed-stream primitive has been added and tested for partial, coalesced, oversized and malformed messages and frame deadlines. A private same-user recovery endpoint is tested separately. These primitives have not yet been integrated into a production watchdog event loop or tested for airborne owner adoption; no real-flight watchdog claim is made.

A disarmed live-camera session produced current JPEG preview frames using the macOS FFmpeg adapter and closed cleanly. The supervised demo includes a loopback-only, tokenized browser preview and requires a live preview before arming. A subsequent test found an existing unresolved prior-flight incident; its journal records takeoff and a landing request, but not confirmed ground. The incident and retained owner were preserved. A disarmed camera test used a separate temporary incident directory and therefore did not consult that existing record; future tests must use the same per-aircraft incident store. No further aircraft actions should be taken until the operator verifies the aircraft's physical state and recovery is completed through the supervisor.

After the operator confirmed the aircraft was physically grounded, an attempted recovery did not obtain the fresh control-ready stopped-motor telemetry needed to clear the earlier incident. The record remains active. A separate viewer attached only to JPEG files already produced by an existing camera session; an actual frame was verified in the local browser. A separate video-only owner was blocked by the existing incident lock, preventing concurrent ownership. No flight commands were sent during the viewer test.

The operator later confirmed ground through the supervisor, which resolved the prior incident, but the demo then attempted to arm while the controller still held the `unresolved_previous_flight` fault. The demo now resets only that fault after the supervisor confirms recovery is no longer required and the aircraft is not possibly airborne. Other faults remain blocking. A real-drone disarmed run reached the operator confirmation prompt with live video, then declined authorization and closed with cleanup verified; it sent no arm, takeoff or landing intents. Regression tests cover this transition and refusal to reset unrelated faults.

The operator reported that a subsequent flight required placing a hand underneath the drone to complete landing. The flight journal records an acknowledged landing request followed by an unconfirmed landing, then operator ground attestation; the incident was resolved. The demo now offers the reference client's additional landing-confirmation action once, only on explicit operator input and while the supervisor reports fresh confirmation availability. This action has been tested in simulation, not yet verified on the aircraft. The demo also reports a disconnected drone Wi-Fi route and waits briefly for initial battery telemetry rather than immediately failing when the video stream arrives first. Following a drone restart and physical Bluetooth confirmation, a disarmed run reached the readiness prompt with video; flight was explicitly declined.

The operator requested repeated ordinary landing commands. The demo can now make at most two further requests at least five seconds apart, only when the previous landing was acknowledged, no command is pending, the control link is available, and fresh motion and control telemetry still report the aircraft flying with motors on. It does not automatically retry a missing acknowledgement or issue forced landing. Explicit landing confirmation, when offered, takes priority and remains operator-controlled. This behavior is verified with simulated tests and the reference loopback recovery test; it has not been flight-tested on the aircraft.
